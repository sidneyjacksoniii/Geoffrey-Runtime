# Geoffrey Runtime and Jackson-West evidence boundaries

**Evidence snapshot: 8 November 2026**

This matrix distinguishes what is present, isolated-tested, deployed, owner-observed, live-verified, staged, planned, or unresolved. “Live-verified” is deliberately narrow and does not imply continuous availability, universal coverage, production readiness, or customer scale.

| Deterministic intake, governance, and routing | Code-present; selected isolated tests; selected live evidence in dated case studies | Known requests use bounded handlers and policy. This is not proof of universal route coverage. |

## Interpretation rules

- **Code-present** means implementation exists; it does not establish deployment.
- **Isolated-tested** means selected behavior passed bounded tests outside a universal production rollout.
- **Inspected** means an installed component or graph was read; it does not establish an end-to-end successful run.
- **Deployed** means a component was placed in a live environment; deployment alone does not prove an effect.
- **Owner-observed** means the owner reports or directly observed selected behavior; the supporting receipt class may be narrower.
- **Live-verified** means a selected path produced matching runtime evidence. Scope is limited to the path described.
- **Staged, disabled** means a candidate exists and may have passing tests but is not active production behavior.
- **Planned** means future work, not a current control.
- **Unresolved** means the design, migration, or evidence still has an open gap.

Sanitized examples in this documentation are explanatory summaries, not production records. Passing isolated tests are never described as live operations.
